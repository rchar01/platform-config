# GitLab PKI Package Exchange

`scripts/platform-pki-gitlab-package` is the controller-side transport helper
for host-local PKI Generic Packages. The current implementation publishes only
one exact request package. It does not collect files from a target, create a
collection receipt, approve or sign a request, retrieve a response, activate a
certificate, or contact GitLab unless an operator explicitly invokes it.

The canonical transport design remains
`platform-tools/docs/pki-gitlab-package-exchange.md`. Stop if that contract and
this implementation disagree.

## Request Package

The helper reads one protected outside-Git workspace:

```text
<exchange-root>/<service>/<request-id>/
|-- trust/
|   |-- policy
|   |-- requesters.allowed_signers
|   |-- approvers.allowed_signers
|   |-- responses.allowed_signers
|   `-- deployers.allowed_signers
`-- request/
    |-- tls.csr
    |-- request
    |-- request.sig
    |-- collection-receipt
    `-- stage-manifest
```

Every directory is owned by the invoking controller user with mode `0700`.
Every file is singly linked, owned by that user, and mode `0600`. The exchange
root must be an absolute canonical path outside this repository. The request and
trust directories must contain exactly the listed files; `tls.key`, extra
entries, links, alternate names, and unsafe metadata fail before a network
request.

The collection phase must create the canonical receipt with `transport=ssh` and
the exact independently enrolled SSH host-key digest. The manifest must use the
canonical request-stage schema and list, in order, `tls.csr`, `request`,
`request.sig`, and `collection-receipt`. Neither file is generated by the
package helper in this implementation.

Before publication, the helper independently verifies:

- canonical request, collection-receipt, policy, and stage-manifest records;
- request identity, lifetime, operation, profile, and response principal;
- the reviewed inventory digest, common name, ordered DNS/IP SANs, CSR
  signature, SHA-384 signature algorithm, EC P-384 key, extensions, and SPKI
  digest;
- exactly one LF-terminated CSR and SSH-signature ASCII-armored object, with no
  prefix, suffix, additional object, or unconsumed decoded bytes;
- the detached request signature against frozen requester trust;
- exact schema-2 policy and no-options Ed25519 allowed-signers grammar;
- requester/deployer membership, sole approver/response principals, and all
  request, signature, CSR, transport-host-key, and five trust digests;
- protected source identities, file type, ownership, mode, link count, and bytes
  before, during, and after publication, plus protected directory identity,
  ownership, and mode.

The reviewed inventory digest and requested identities must be provisioned in
one protected mode-`0400` or mode-`0600` controller record. Repeated SAN fields
are ordered and the counts are exact:

```text
schema=1
kind=pki-request-inventory
service=registry-dev
target=dev-registry-01
inventory_sha256=<64-lowercase-hex>
common_name=registry.dev
dns_san_count=2
dns_san=registry.dev
dns_san=dev-registry-01
ip_san_count=1
ip_san=192.0.2.61
```

This prevents a reviewed inventory digest from being combined with unrelated
caller-selected CN or SAN values.

## GitLab Prerequisites

The selected design requires self-managed GitLab CE image
`18.11.3-ce.0`, one dedicated private project, and Generic Packages enabled.
Before using the helper against any instance, independently verify that:

- the configured HTTPS origin, numeric project ID, and project path identify the
  dedicated exchange project;
- Generic duplicate publication is disabled without a matching exception;
- `pki-exchange-*` Generic Packages are protected from unauthorized push and
  deletion;
- package cleanup is disabled;
- the publisher credential cannot delete packages or change project, package,
  token, protection, or membership settings;
- the exact deployed GitLab patch version passes disposable integration tests.

Provision the selected origin, project ID, path, and version in one protected
mode-`0400` or mode-`0600` controller record owned by the invoking user:

```text
schema=1
kind=pki-exchange-project
origin=https://gitlab.example.test
project_id=123
project_path=platform/pki-exchange
gitlab_version=18.11.3-ce.0
```

The helper requires this exact record and uses only its numeric project ID in
API endpoints. Before any package query, it performs one tightly allowlisted
`GET /api/v4/projects/<id>` and requires the returned numeric ID,
`path_with_namespace`, and `web_url` to match the protected record exactly. It
does not inspect package protection, duplicate, cleanup, token, membership, or
other project configuration and does not provision the project. Those controls
remain independent operator gates.

Use a protected CI job token where possible. A project access token with `api`
scope is a broader fallback. The helper intentionally does not accept deploy
tokens because deploy tokens cannot enumerate the package and package-file REST
metadata required for fail-closed publication.

Store the token in an outside-Git, singly linked regular file owned by the
invoking user with mode `0400` or `0600`. Store the reviewed GitLab CA bundle
outside Git. Token bytes are read directly by the helper and never accepted in
argv, URLs, payloads, or output.

## Publication

The command is an inert template. It is not authorization to contact the
homelab GitLab instance or publish a real request.

```bash
scripts/platform-pki-gitlab-package publish-request \
  --exchange-root /outside-git/pki-exchange \
  --service registry-dev \
  --target dev-registry-01 \
  --request-id 0123456789abcdef0123456789abcdef \
  --inventory-record /outside-git/config/registry-dev-request-inventory \
  --transport-host-key-sha256 64-lowercase-hex \
  --project-record /outside-git/config/pki-exchange-project \
  --token-type job \
  --token-file /outside-git/secrets/pki-exchange-job.token \
  --ca-file /outside-git/trust/gitlab-ca.crt
```

The package coordinate is derived rather than supplied:

```text
name=pki-exchange-request-<service>
version=<request-id>
```

The helper queries all six GitLab 18.11 package statuses and consumes every
pagination link. It accepts exactly one exact `default` package or an absent
coordinate. Existing files must be a digest-identical subset of the protected
local package. Missing files are uploaded in canonical order with
`stage-manifest` last. A complete matching package is an idempotent no-op.

Ambiguous objects, blocked or unknown status, duplicate names, extra files,
changed digests, malformed metadata, uncertain HTTP results, redirects, and
cross-origin or altered pagination fail without deletion or repair. The helper
never selects newest, latest, first, last, or a neighboring coordinate.

## Remaining Gates

This request publisher is not an end-to-end exchange. The following remain
blocked:

- protected CI `resource_group` serialization;
- disposable runtime qualification against exact GitLab `18.11.3-ce.0`;
- request download and controlled-media custody records;
- approval, response, and evidence package operations;
- private inventory, credentials, project configuration, and live publication.

The separate Ansible host-local workflow now performs descriptor-pinned target
collection and creates the canonical collection receipt. Outside this package
helper, it also authenticates a protected local response, performs interactive
target activation and journal-bound recovery, validates Zot from one distinct
runner, and exports authenticated evidence. This helper still does not retrieve
requests or responses from GitLab, import signer outcomes, or publish response
or evidence packages.

Do not run a live request or package publication until the remaining GitLab,
controlled-media, private-configuration, and authorization gates are complete.
