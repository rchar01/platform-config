# Roles

Roles are intentionally variable-driven. Real environment values come from `platform-private`; public role defaults must remain non-secret. Software installed directly by a role must be version-pinned through role variables unless an explicit one-off discovery override exists. OS package roles accept configurable package specs; reproducible OS package versions require pinned repositories, snapshots, or versionlock outside individual role defaults.

- `rocky_repository_policy`: optional read-only validation of the exact effective DNF release version, enabled repository IDs, origins, local signing-key URLs, and signature-check settings. HTTPS is the default; an explicit disabled-by-default HTTP `baseurl` exception retains exact comparison and local-key enforcement without authenticating metadata transport. Mirrorlists, metalinks, and signing keys remain strict. Package-consuming roles depend on this gate; when private inventory enables it, repository drift fails before package operations. It never edits repository definitions or loads repository metadata, does not verify signing-key bytes, and URL validation alone does not make mutable mirror content immutable.
- `common`: shared OS defaults such as timezone, platform directories, optional managed `/etc/hosts` aliases, baseline logrotate compression, and optional MOTD. MOTD removal is explicit through `platform_motd_remove_when_empty`.
- `users`: optional automation and admin users from inventory variables. When keys or groups are configured, defaults favor exact managed state rather than additive access, and previously managed admin sudo/key entries are pruned from a host manifest.
- `ssh`: SSH server installation, service management, and managed drop-ins. Previously managed drop-ins are pruned when `ssh_config_dropins_prune_managed` is true.
- `packages`: additive common package installation from `platform_base_packages`. Package removal is intentionally not automatic. The public examples keep the shared baseline small; role-specific runtime packages belong in role variables, not the global base package list.
- `root_lvm`: optional desired-state management for an LVM-backed root filesystem. It can converge template-created root partitions, PVs, LVs, and filesystems to consume the declared boot disk capacity. It is disabled by default and requires explicit private inventory variables for the target disk, partition, PV, VG, and LV.
- `firewalld`: installs firewalld and its Python bindings, verifies binding imports, and manages systemd enabled/runtime state. The default baseline is disabled and stopped while service roles maintain permanent rules offline; inventories can opt into active enforcement after validating live rules. Previously managed generic entries are pruned when `firewalld_prune_managed` is true. See [Firewalld Readiness And Enablement](firewalld.md) for the future activation workflow.
- `chrony`: chrony installation and service management.
- `storage_volume`: LVM-backed persistent storage volume management. It uses stable private disk paths, creates XFS filesystems by default, and mounts by filesystem UUID. Optional multi-volume layouts provide one disk/VG initialization decision, explicit allocation bounds, and required unallocated VG headroom. A guarded `reuse_existing_vg: true` layout can add missing LVs to a reviewed existing one-PV VG only after read-only canonical-device, topology, identity, existing-LV/filesystem, and aggregate free-space checks; it requires `initialize: false` and never changes partitions or VG membership.
- `nfs_client`: client-side NFS mount management from `nfs_client_mounts`.
- `container_runtime_kernel`: environment-neutral OverlayFS prerequisite for container runtimes. It manages an auditable, enabled-by-default systemd policy exception without changing third-party modprobe configuration, and its opt-out proves normal module loading before fail-closed removal.
- `podman_host`: Podman host foundation for service containers. It depends on `container_runtime_kernel`, requires and verifies an exact Podman NEVRA, supports deliberate downgrade, manages the corresponding DNF versionlock while preserving unrelated locks, creates the system Quadlet directory, and manages the Podman socket when `podman_host_socket_manage` is true.
- `registry_client_tools`: Pinned client tooling for registry smoke tests on `registry_clients`, currently Helm for OCI chart push/pull checks.
- `pki_host_local_certificate`: operator-only target-local Zot certificate lifecycle. It installs schema-3 four-file trust, publishes schema-2 requests directly from the target to one private GitLab Generic Package project, downloads and authenticates responses on the target, installs the digest-pinned reviewed Zot validation CA, recovers activation journals, validates Zot locally, and rolls back failed activation. Ansible never carries package or token bytes.
- `zot_registry`: Zot OCI registry deployment as a system Podman Quadlet service with operation-aware, target-state-derived dormant, managed, or authenticated host-local TLS custody, optional htpasswd authentication, optional UI, persistent storage, service lifecycle, and guarded broad or source-scoped firewalld management.
- `openbao`: disabled-by-default three-node OpenBao `2.6.1` service foundation with immutable image identity, host networking, strict retry-join TLS, storage-mount preflight, native candidate validation, and reconciled backend/cluster firewall policy. The guarded OpenBao playbook can stage the complete foundation only for the full three-node group while all services remain stopped.
- `openbao_haproxy`: disabled-by-default native HAProxy `3.0` foundation for OpenBao TCP passthrough, active-only strict HTTPS backend checks, source-restricted metrics, atomic candidate validation, and reconciled listener firewall policy. The guarded OpenBao staging playbook invokes it after the direct service role and before Keepalived.
- `monitoring_haproxy`: disabled-by-default host-native monitoring HAProxy lifecycle. It validates the complete frontend/backend authorization contract, installs and version-locks exact HAProxy `3.0.5`, publishes PKI/config/map content-addressed bundles only after native validation, atomically switches and rolls back active generations, adds SELinux listener labels, reconciles manifest-owned firewalld rules, and keeps service activation behind explicit lifecycle and live-firewall readiness gates. Disposable fixtures cover exact rendered behavior and Rocky systemd convergence without authorizing managed-host rollout.
- `openbao_status`: controller-side, read-only OpenBao status gate requiring one initialized and unsealed active node, two initialized and unsealed standbys, exactly three expected Raft voters, stable leadership and configuration index, strict direct-node TLS, and an outside-Git token limited to reading `sys/storage/raft/configuration`.
- `gitlab_ce`: GitLab CE deployment as a system Podman Quadlet service with HTTPS, persistent storage, Git-over-SSH port mapping, service lifecycle, and permanent firewalld port management.
- `gitlab_runner`: GitLab Runner deployment as a system Podman Quadlet service. It registers one executor with a pre-created runner authentication token stored outside Git. The default shell mode is socket-free; an explicit Docker mode can mount the role-managed rootful Podman socket into the manager only, requires immutable job images and per-build networking, and keeps privileged jobs, host bind volumes, and job-level socket access disabled.
- `node_exporter`: Prometheus Node Exporter installation as a host systemd service for VM-level metrics without requiring Podman on Kubernetes nodes.
- `grafana_alloy`: disabled-by-default single host-native Grafana Alloy `1.18.1` process owner. It pins the official RPM by SHA-256 and exact NEVRA, validates the complete candidate before replacement, and accepts typed feature contributions. The guarded OpenBao-observer playbook can stage or explicitly activate it on all three OpenBao hosts without activating OpenBao itself.
- `platform_external_probe`: disabled-by-default, detect-only strict HTTPS, read-only PostgreSQL-primary, Garage semantic-canary, and node-local VIP-ownership contribution for the shared Alloy process. The guarded OpenBao-observer workflow composes it before Alloy and derives all configured timer states from one explicit activation selector. It never repairs, promotes, fences, or changes Keepalived eligibility.
- `monitoring_stack`: retired combined Prometheus, Loki, and Grafana implementation retained temporarily while replacement HA roles are developed. No active playbook invokes it.
- `monitoring_etcd_status`: strict read-only three-member marker, bundle, persistent enablement, service, container, membership, leadership, and direct mTLS endpoint status gate.
- `rke2`: RKE2 Kubernetes base cluster installation for server and agent nodes. It requires an explicit `rke2_version` pin by default, preserves guarded kernel-module package and reboot handling, consumes the shared container-runtime OverlayFS policy after kernel verification, manages `br_netfilter` and Kubernetes sysctls, and supports Calico, external token files, registry CA configuration, and permanent firewalld rules. Bundled Traefik is the default platform ingress controller and is configured with fixed NodePorts for the external workload load balancer.
- `rke2_kube_vip`: RKE2 kube-vip API HA add-on. It writes a pinned kube-vip HelmChart manifest to the RKE2 bootstrap server, keeps service LoadBalancer support disabled by default, and verifies the API VIP routes through the configured server interface.
- `kong_ingress`: optional RKE2 HelmChart-based Kong Gateway and Kong Ingress Controller alternative for classic Kubernetes `Ingress`. Selecting it disables packaged RKE2 ingress controllers. It exposes the same fixed HTTP/HTTPS NodePorts as Traefik and intentionally defers Gateway API CRDs to a later platform phase.
- `haproxy_workload_lb`: native HAProxy workload load balancer for external VM-to-worker NodePort traffic. It models the production F5 pattern by forwarding `80/tcp` and `443/tcp` to the selected Kubernetes ingress controller's worker NodePorts.
- `keepalived_vip`: disabled-by-default shared unicast VRRP foundation for OpenBao and monitoring. It enforces all-`BACKUP` plus a five-minute delayed automatic failback, exact package identity, hard-fault local HAProxy/listener tracking, peer-scoped protocol `112` firewall policy, and native candidate validation while leaving service activation to later acceptance gates.
- `bastion_host`: base package installation and `/opt/platform` layout creation.
- `k8s_bastion_access`: installs external Kubernetes CLI tools, copies the vendored `platform-k8s-bastion` runtime, writes `/etc/bastion` files from private inputs, installs the login profile, configures policy-driven users, and manages bastion systemd services/timers.

See [Kubernetes Bastion](k8s-bastion.md) for the detailed bastion role workflow.
